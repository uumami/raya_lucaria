# Graph Directed Edges Design

## Context

The old `main` graph used Cytoscape target arrows, so the direction of a relationship was visually legible. The current static graph has stronger local constraints and richer edge kinds, but its SVG edges are plain lines. Readers can see that two pages are connected, but they cannot quickly see which page points to which page without inspecting the detail lists.

## Decision

Add local SVG arrowheads to graph edges.

The arrowheads are generated by the existing `graph.js` renderer at runtime from embedded graph payload data. No graph schema changes are required. No external library, fetch, CDN, storage, worker, ranking, or adaptive behavior is added.

## Behavior

- Every visible graph edge uses `marker-end` to indicate edge direction.
- Arrowheads use the same source-group color as the edge line.
- Edge kind classes remain unchanged:
  - navigation
  - content
  - prerequisite
  - parent
- Search, inspection, dimming, and selected-neighborhood classes continue to apply to the line.
- List layout still hides the SVG graph and clears the canvas.
- The legend names the direction cue as structural graph direction, not learner guidance.

## Constraints

- Do not import Cytoscape, D3, or any other graph dependency.
- Do not fetch graph data at runtime.
- Do not persist graph state.
- Do not modify `data/graph.json`.
- Keep arrowheads readable but restrained to avoid dense-graph clutter.
- Maintain browser/static parity and local deployment behavior.

## Test Strategy

- Contract tests assert that generated graph HTML describes direction and that graph JS contains marker generation without external dependencies.
- Browser tests assert that SVG marker definitions are created, edge lines reference `marker-end`, marker colors match the edge color variable, edge kind classes remain present, and no extra requests occur.
- Existing render-debug and archive gates cover broader static parity, screenshots, overflow, raw math leakage, and no external renderer requests.
